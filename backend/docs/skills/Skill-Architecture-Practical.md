# Skill 功能设计：让 ERP Agent 从“会调用工具”变成“会按规则办事”

> 工具解决“能不能做”，Skill 解决“应该怎样做”。在 ERP 场景中，前者让 Agent 能查询物料、创建订单或分析采购数据，后者确保它在正确的时机、以正确的顺序、遵守正确的字段和审批规则完成工作。

用户说“采购 20 个刹车片”，系统不能只把它理解成一次 `create_order` 调用：物料是否已在 ERP 中确认？是否缺少型号或规格？订单字段是否完整？审批是否已经通过？同样，用户说“对比三家供应商”，系统也不能只拿到一份文档就给出价格结论，必须先查询内部 ERP 数据，再决定是否进入复杂分析和图表流程。

当前项目用 Skill 将这些可复用的业务步骤从系统提示词中拆出，并与 Memory、Tools、RAG 形成分工。

## Skill 是什么

Skill 是一个可复用的 Agent 能力包：以 `SKILL.md` 为核心，将某类通用能力或领域流程的操作步骤、决策条件、输入输出约束和可选参考资源集中沉淀。它不是每轮都注入 Prompt 的固定指令，而是在请求匹配时按需加载。

将通用能力沉淀为 Skill 的直接收益是减少 Prompt 的常驻上下文。例如，订单字段校验、供应商建档、复杂采购分析和图表协议不必出现在每一次闲聊、简单查询或知识问答中；只有任务进入相应流程时，Agent 才读取对应 Skill。后续扩展业务功能时，将新增流程作为独立 Skill 接入，而不是持续堆叠到主 Prompt，从而避免上下文随功能数量线性膨胀。全局且不可省略的安全、委派和审批前置规则则继续留在 Memory。

这种分离也为持续稳定运行提供基础：稳定的步骤、判断条件、失败路径和对客状态被版本化地沉淀在 Skill 中，Agent 不需要在每轮请求中重新推导同一套业务规则；功能之间按领域隔离，修改一个 Skill 不应改变无关流程的执行依据。

## 一、为什么不能只靠系统提示词和工具

把所有业务规则写进主提示词，起初很直接，但会很快遇到三个问题：

| 问题 | 表现 | 结果 |
| --- | --- | --- |
| 上下文膨胀 | 每轮都带上订单、供应商、分析和图表的全部规则 | 无关任务也承担 token 和理解成本 |
| 规则串扰 | 供应商查询受订单字段约束，简单查询被复杂报告模板干扰 | 行为不稳定、回复冗长 |
| 权责不清 | 文档、工具、审批和实时数据混在一起 | 容易把流程说明误当成 API 权限或事实依据 |

Skill 的目标不是增加一层“说明书”，而是将特定业务流程按需交给对应执行单元。它只能指导已注册能力的使用，不能凭文档创造工具、扩大 API 权限或跳过审批。

## 二、当前系统的四层分工

系统将不同性质的信息放在不同层：

```text
Memory       所有请求都必须遵守的全局规则和委派约束
Skill        某个业务流程的步骤、字段校验、报告和图表契约
Tools        实际执行 ERP 查询、写入、文件和计算的原子能力
RAG          已入库文档知识的检索、改写、融合和引用
```

| 层 | 当前实现位置 | 解决什么 | 不负责什么 |
| --- | --- | --- | --- |
| Memory | `src/agent/memory/AGENTS.md` | 委派格式、物料解析前置条件、长期记忆边界 | 订单字段明细、图表协议等领域细节 |
| Skill | `backend/skills/` | 领域工作流与失败路径 | 注册工具、执行权限、实时事实 |
| Tools | 工具注册表与子 Agent YAML | 查询、创建、审批前调用和计算 | 自行决定业务流程 |
| RAG | `src/agent/rag/` | 流程、规则、字段含义等文档知识 | 当前库存、订单状态、今日价格 |

这一分层决定了一个基本原则：**流程由 Skill 约束，事实由工具确认，文档知识由 RAG 补充，跨请求规则由 Memory 固化。**

## 三、Skill 如何按领域加载

当前技能库位于 `backend/skills/`，运行时由 `FilesystemBackend` 映射为 `/skills/`：

```text
backend/skills/
├── main/
│   └── skill-management/             # 后续用户自助扩展能力的规划入口
├── procurement/
│   └── procurement-analysis/         # 多维分析、图表与复杂报告
├── order/
│   └── order-management/             # 订单信息收集、校验与审批前 payload
└── supplier/
    └── supplier-management/          # 供应商查询、建档与审批前 payload
```

每个业务 Skill 的入口都是 `SKILL.md`。采购分析将图表 JSON 契约拆到 `reference/chart_params.md`，仅在图表任务中读取。这对应渐进式加载的三个层次：

| 层次 | 加载内容 | 当前价值 |
| --- | --- | --- |
| 元数据 | Skill 名称和描述 | 让 Agent 判断是否相关 |
| 核心正文 | `SKILL.md` | 提供完整流程、判断条件和对客状态 |
| 参考资源 | `reference/`、`scripts/`、`assets/` | 仅为复杂契约或确定性任务加载 |

### 主 Agent 与子 Agent 的边界

主 Agent 只挂载 `/skills/main/`。三个业务执行 Agent 均为自定义子 Agent，因此各自显式声明可见的领域路径：

```text
用户请求
  │
  ▼
主 Agent: /skills/main/
  ├─ 创建或更新采购订单 ───► procurement_order: /skills/order/
  ├─ 查询或新建供应商 ─────► supplier_manager: /skills/supplier/
  └─ 采购价格、历史订单、库存分析
                         └► procurement_analyst: /skills/procurement/
```

这样，订单 Agent 不会因为加载采购分析模板而生成无关报告，分析 Agent 也不会获得供应商建档的工作流。`subagents/loader.py` 对 YAML 中的 `skills` 字段做非空字符串校验，再将路径传给 Deep Agents。

## 四、Memory 为何不替代 Skill

`/memory/AGENTS.md` 在构建 Agent 时作为 Memory 加载，它描述的是无论请求类型都必须遵守的条件，例如：

1. 委派任务必须使用精确的子 Agent 名称和固定描述模板。
2. 用户创建采购订单但未提供已确认的 ERP `partId` 时，必须先让 `procurement_analyst` 做物料识别。
3. 物料候选不唯一或未找到时，向用户询问型号、规格或供应商等业务信息，不要求其提供数字 ID。
4. 用户偏好写入 `/memories/preferences.md`，而不是修改共享 Skill。

这些规则必须每轮生效，适合放在 Memory。反之，订单字段规则、供应商 payload 限制和图表 JSON 协议只在特定任务出现，适合留在领域 Skill。将它们全部放到 Memory，会削弱渐进式加载的意义。

## 五、Skill 不拥有工具权限

Skill 文本可以规定步骤，但真正的行为边界仍在工具和运行时：

| 场景 | Skill 规定 | 运行时保证 |
| --- | --- | --- |
| 创建/更新订单 | 收集字段、校验草稿、剔除禁止字段 | `create_order`、`update_order` 触发 `approve/reject` 审批 |
| 新建供应商 | 校验必填信息，审批和 ERP 成功前不宣称已创建 | `create_supplier` 触发 `approve/reject` 审批 |
| 查询供应商 | 只读查询并如实返回结果 | 不调用创建工具 |
| 采购分析 | 先查 ERP 再计算，样本不足时说明缺口 | 仅使用本次工具实际返回的数据 |

`build_runtime_permissions()` 拒绝对 `/skills/**` 的写操作。因此 Agent 可以读取审核后的共享 Skill，但不能在运行中修改、删除或临时生成 Skill。审批也由 `interrupt_on` 和工具调用链执行，不能依赖文档文字实现。

## 六、Skill 与 RAG：流程规则和事实来源不能混淆

RAG 解决的是“知识库如何找到更相关的文档”，Skill 解决的是“拿到知识后如何按业务规则行动”。两者配合，但不能互相取代。

### 查询改写为文档知识增加入口

当前 RAG 保留用户原问，并按四个视角做保守扩展：

```text
用户：P-100 的刹车皮能不能装到 X2 上？

original：P-100 的刹车皮能不能装到 X2 上？
semantic：P-100 制动片与 X2 车型是否兼容、是否适配
keyword：P-100 X2 刹车片 制动片 兼容 适配
intent：查询 P-100 制动片安装到 X2 车型的适配关系、限制条件和依据
```

每个有效视角同时经过 Dense 与 Sparse/BM25 检索，再使用加权 RRF 融合。`original` 权重最高；改写为空、重复、非 JSON 或服务不可用时，系统回退为只检索原问题，而不是中断会话。

### RAG 不能替代 ERP 工具

| 用户问题 | 正确来源 | RAG 的辅助作用 |
| --- | --- | --- |
| “当前库存还有多少？” | 已注册 ERP 查询工具 | 解释库存字段或补货流程 |
| “ORD-9527 是否已发货？” | 已注册订单查询工具 | 解释订单状态含义 |
| “P-100 能否装到 X2？” | 知识库适配规则，必要时 ERP 物料确认 | 提供兼容性依据和限制条件 |
| “如何申请退货？” | 知识库流程规则 | 直接检索退货、售后和退款规范 |

`prompts.py` 还明确将检索内容标记为不可信参考资料：它只能在支持回答时使用，并需要引用 `source_id`。因此，Skill 不能根据 RAG 文本虚构价格、交期或供应商表现，也不能把查询改写当成权限过滤或结构化筛选。

## 七、一次采购请求如何经过各层

以“采购 20 个某型号刹车片”为例：

```text
用户请求
  │
  ├─ 有已确认的 ERP partId ─────────► procurement_order
  │                                    读取 order-management
  │                                    校验字段 → 触发审批 → ERP 写入
  │
  └─ 没有已确认的 ERP partId ───────► procurement_analyst
                                       part_search / part_query
                                       ├─ MATERIAL_RESOLVED
                                       │    └─ 带物料信息进入订单委派
                                       ├─ MATERIAL_AMBIGUOUS
                                       │    └─ 展示候选并询问型号、规格或供应商
                                       └─ MATERIAL_NOT_FOUND
                                            └─ 请求更准确的业务描述
```

如果用户追加“它是否适配 X2”，RAG 可依据知识库提供适配规则。订单所需的 `partId` 仍必须由 ERP 查询确认。这避免了把检索内容误当成当前系统记录。

## 八、skill-management 的规划定位

`main/skill-management` 服务于后续“用户自行增加或分配 Skill”的能力，而不是当前对共享目录开放任意写入。设计中的流程是：

```text
用户提出新增/调整 Skill
  → 在沙箱中下载、创建或修改候选内容
  → 验证流程、工具契约和安全边界
  → 持久化到 /persistence
  → 调用 assign_skill 分配给目标子 Agent
```

用户未指定目标子 Agent 时，默认分配给主 Agent。该设计保留了用户扩展能力，同时确保候选内容经过验证和分配，避免直接写入共享 `/skills/**` 目录。

现阶段仍应遵守两个限制：

1. 共享 Skill 由运行时权限保护，用户和 Agent 都不能直接改写 `/skills/**`。
2. 新 Skill 不能仅靠文档声明新 API；若需要新的业务能力，必须先定义 Swagger operation、加入显式工具注册表并补充 `MockTransport` 测试。

## 九、常见设计错误

| 错误 | 表现 | 正确做法 |
| --- | --- | --- |
| 将所有规则写进系统提示词 | 简单查询也携带大量领域细节 | 将全局约束放 Memory，将领域流程放 Skill |
| 用 Skill 代替工具注册 | 文档要求调用未注册 API | 先定义并注册工具，再编写 Skill 流程 |
| 用 RAG 代替实时查询 | 用文档判断库存、发货状态或当前价格 | 使用 ERP 工具获取事实，RAG 只补充规则说明 |
| 让改写丢失精确实体 | `P-100` 变成泛化“制动零件” | 保留原问，并让 keyword 原样保留编码和约束 |
| 让 Agent 直接写共享 Skill | 未审核内容影响其他会话 | 维持 `/skills/**` 只读，走受控的 skill-management 流程 |
| 用文字替代审批 | 文档说“需要审批”但工具直接写入 | 在 `interrupt_on` 和工具调用链中实施审批 |

## 十、设计结论

Skill 不是工具权限的另一种写法，也不是 RAG 文档的副本。当前 ERP Agent 用它承载按需加载的领域工作流：Memory 保证全局约束，Tools 提供受控执行，RAG 提供可引用的文档知识，Skill 则将它们组织为可重复、可审计的业务过程。后续业务功能通过独立 Skill 扩展，既避免主 Prompt 膨胀，也让每项能力拥有稳定、可维护的执行依据。

后续的 `skill-management` 将把这种能力扩展给用户，但仍应坚持“先验证、再持久化、后分配”的受控路径。
